# W2.18 T1 evidence — durable release artifacts

**Date:** 2026-08-07<br>
**Scope:** local implementation and verification only<br>
**Remote publication status:** not executed or claimed

## Implemented release truth

- `scripts/lib/deployable-images.mjs` is the single six-artifact inventory. `node-api` and
  `job-worker` deliberately share `node-backend`; `migrations` uses its own least-privileged image.
- `scripts/release-images.mjs` publishes full-source-SHA tags to GHCR with Buildx `--push`, reads
  registry digests from Buildx metadata, and writes log-free exact-key JSON to an external path.
- `.github/workflows/release-image.yml` has only `contents: read` and `packages: write`, authenticates
  to GHCR with the repository token, and uploads the digest document separately from build logs.
- `docker-compose.release.yml` removes all seven application `build` definitions and requires six
  immutable image references. Both Node roles consume the same exact reference.
- `scripts/release-deployment.mjs` preserves distinct candidate and previous digest manifests,
  renders either slot as a Compose environment, and verifies configured references plus local image
  IDs/repository digests for every runtime container. The completed one-shot migration container is
  accepted only with exit code zero.
- ADR-0022 now records durable GHCR artifacts and explicitly supersedes ephemeral runner-local tags.
- `cutover-readiness.mjs` no longer treats a generic image build/push as a rollback artifact; it
  requires durable publication, no-build consumption, candidate/previous selection, and actual-image
  verification support.

## Remaining external proof

This evidence does not claim that GHCR packages were published, pulled onto a deployment host, or
used in a timed rollback. Those require the remote release workflow and the W2.18 T3–T5
candidate-image/canary/rollback evidence. W2.18 therefore remains open.
