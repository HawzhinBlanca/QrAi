# Deep architecture audit — Flutter + Node consolidation

**Date:** 2026-08-06<br>
**Scope:** repository structure, product clients, API migration, realtime/audio, inference, deployment, tests, and deletion safety.<br>
**Method:** read-only symbol/reference mapping, topology and workflow inspection, live cutover checker, and targeted contract tests. No runtime code was changed.

## Executive verdict

Do not create a new project. The correct move is a controlled clean-in-place consolidation.

The repository is not bad because it is a monorepo. It is bad because it currently contains three generations of client, two API implementations, two mobile strategies, two incomplete deployment stories, and several experiments while the default commands still launch the old generation. The safety engineering is materially better than the product/runtime coherence.

Starting over would throw away the most valuable parts: immutable Quran data and Unicode traps, RLS migrations, privacy and learner-feedback gates, Rust integration behavior, 294 API-parity tests, cross-language fixtures, and the working Flutter foundation. A new repository would still have to import those assets, at which point it would be this repository with less history and more risk.

## 1. The actual system today

The desired architecture says “Flutter + Node.” The executable repository says something else:

- `pnpm dev`, `build`, `test`, `typecheck`, and `preview` are centered on `apps/web`.
- `docker-compose.yml` starts Postgres, Rust `platform-api`, Rust `realtime-gateway`, Node `ml-inference`, Python `asr-inference`, and React `web`.
- `scripts/release-images.mjs` builds exactly those five application images; it does not build Node API or Flutter.
- CI does compile a Flutter Android APK, but it is debug-signed and retained as a short-lived artifact, not a distributable product release.
- `services/node-api` has no package manifest, workspace membership, Dockerfile, Compose service, nginx target, or release image.
- Node listens on `127.0.0.1:8099`, requires `PLATFORM_API_UPSTREAM`, and defaults `NODE_API_PORTED` to empty.

So the migration has produced substantial code but not changed the operating system of the repository. That is why the project feels like “a few structures instead of one system.”

## 2. The most serious finding: the cutover proof is false-green

The Rust router exposes 42 method/path pairs. The contract tooling reports 40.

`routePairsFromRust` splits only when `.route(` is followed by whitespace and a quote. Two newer registrations put explanatory comments between `.route(` and the path, so the parser silently drops:

- `GET /v1/tajweed-findings/{id}/audio`
- `POST /v1/audio-chunks`

This produces a chain of false confidence:

- OpenAPI describes 40 operations, not 42.
- Contract tests explicitly pin 40.
- Cutover reports 40/40 boundary-oracle coverage.
- Node's route-table test compares `PORTABLE` with `ROUTES`, two Node-owned lists, so a route missing from both is invisible.
- The 28 focused contract/cutover/route-table tests pass while the inventory is wrong.

This is not a small documentation defect. Route completeness is the denominator for deciding whether Rust can be deleted.

## 3. Node API: impressive port, not a standalone backend

Node has real handlers for 37 operations with meaningful parity work. The strong parts include tenant-scoped transaction helpers, stale-tenant isolation tests, cross-language ticket vectors, response serialization compatibility, error redaction, and a large black-box A/B suite.

Five live operations remain Rust-only:

1. `POST /v1/auth/register`
2. `POST /v1/auth/login`
3. `POST /v1/audio-chunks`
4. `POST /v1/recitation-sessions/{id}/finalize`
5. `GET /v1/recitation-sessions/{id}/tajweed-findings`

The last three are central to the claimed product:

- Audio indexing connects stored chunks to later teacher playback.
- Finalization fetches the server-held transcript and persists server-derived alignment; it prevents the client from inventing what was heard.
- Session findings are the ownership-scoped learner route that withholds unapproved AI judgments.

Flutter calls finalization and session findings in its main practice flow. Deleting Rust now therefore breaks the flagship path, even if all 37 Node routes were enabled.

### Missing production equivalence on the 37 routes

Handler parity is not service parity. Node still lacks:

- Rust's maintenance kill switch.
- Rust's rate limiting; the parity harness disables the Rust limiter.
- Boot refusal for superuser or `BYPASSRLS` database roles.
- Graceful SIGTERM draining and an explicit DB-pool shutdown path.
- Bounded timeout/cancellation on the fallback proxy.
- Bounded timeout/cancellation on several ML, ASR, privacy, and audio-storage calls.
- A production container, service account, readiness wiring, reverse-proxy route, and release artifact.

The current Node API is best described as a highly tested strangler prototype.

## 4. Realtime is still a separate Rust product

The Rust gateway is not incidental glue. It owns:

- WebSocket upgrade and origin policy.
- HMAC ticket validation and tenant binding.
- single-use/replay defense, including optional Redis coordination.
- bounded per-session channels and backpressure.
- binary frame validation and hostile-input handling.
- bounded forwarding retries and metrics.
- retained-audio storage forwarding and API indexing.

Node only mints a ticket compatible with the Rust validator. `shared-ticket` remains load-bearing while the Rust gateway exists.

The standard Compose configuration also fails to set `PLATFORM_API_URL` on the gateway. Its own configuration treats absence as “indexing off.” Audio can be stored without a corresponding database index, making teacher playback undiscoverable.

A strict Flutter + Node target must port this behavior, not merely delete the directory. The lean answer is a `realtime` module and entrypoint inside the same Node package, held against the Rust gateway's vectors and adversarial tests until cutover.

## 5. Flutter: the right client, not yet the complete product

Flutter is a serious implementation. It has a Quran reader, consent-gated PCM capture, ticketed WebSocket streaming, finalization, reviewed Tajweed rendering, progress reading, privacy export/deletion, and a role-gated teacher review queue. Android release compilation and a substantial Dart test suite exist.

It still cannot replace React as the complete product:

- English is the only declared UI locale; there are no ARB localization bundles.
- Practice takes free-form Surah/ayah numbers instead of continuing from the selected passage.
- No reference-recitation playback or guided listen/imitate/correct/drill loop exists.
- Progress is read-only; a learner cannot record the completed review in Flutter.
- Findings are read immediately after stopping, but there is no later reviewed-feedback inbox.
- Realtime has no complete reconnect/bounded local buffer/batch fallback journey.
- Release builds reject the development bearer token, correctly, but no production enrollment path writes a legitimate token.
- Teacher review lacks retained-audio playback, pagination, strong session context, and the edited-decision workflow.
- Scholar/source approval and minimal model-governance surfaces are absent.
- No signed store candidate, physical Android/iOS microphone matrix, background/interruption proof, or iOS release build exists.

For a “number one Kurdish Quran learning app,” English-only Flutter is a launch blocker, not a polish issue.

## 6. React Web and Expo are not equal kinds of legacy

### Expo: retirement candidate

`apps/mobile` is 661 lines, outside the pnpm workspace, and has only pure helper tests. It has not been proven on a device, does not use its declared secure storage, hand-authors a source checksum, and renders raw alignment feedback without the current learner source/review gate.

Flutter supersedes every defensible Expo capability with stronger consent, realtime transport, secure-token storage, privacy, progress, and review handling.

Expo should be the first source tree retired, after Flutter's physical-device capture and fallback path are proven. Its removal also includes `.github/workflows/mobile.yml`, its verify/proof blocks, and current-state documentation references.

### React: transitional, still load-bearing

React remains the only deployed frontend and owns capabilities Flutter lacks:

- the richer six-step learning flow;
- reference playback and word highlighting;
- real SM-2 progress writes and weekly visualization;
- pilot invite/cookie flow;
- session-specific teacher review and retained-audio playback;
- scholar, benchmark, agent, diagnostics, and governance views;
- the only currently wired Sorani verse-translation path;
- browser, responsive, accessibility, security-header, and full-journey proof.

Do not blindly port every internal dashboard to Flutter. Define the minimum product: learner, teacher review with audio, scholar/source approval, privacy, and operations observability. Delete decorative or duplicative admin surfaces instead of reproducing them.

## 7. Inference and “Node only”

`services/ml-inference` is load-bearing Node code for Quran-constrained alignment, Tajweed rule analysis, audio-object lifecycle, and ASR orchestration. It should become a module/worker entrypoint in the consolidated Node package rather than remain a separately governed mini-project.

`services/asr-inference` is the actual acoustic execution path. The standard deployment deliberately runs generic Whisper `base`, while code also supports a Quran-tuned Hugging Face model. Its `/health` always returns HTTP 200 and communicates readiness only in a JSON `loaded` flag, so Compose can mark a model-less process healthy.

Do not translate PyTorch/Whisper Python into JavaScript merely to reduce the language count. Keep it as one private, replaceable worker until one of these is measured against a Kurdish/Quran recitation evaluation set:

- a Quran-tuned production model in the existing worker;
- ONNX Runtime in a Node worker;
- private on-device Flutter inference.

The product can honestly be “Flutter + Node” at its public application boundary while one isolated model worker remains Python. If the requirement is literally two runtimes, ONNX/on-device replacement is a separate model-evaluation project and must win on accuracy, latency, memory, battery, and privacy before deletion.

`services/tajweed-neural` is experimental, unwired, 605M-parameter research. `services/agents` is operator-only, not containerized, and provides deterministic supervised workflows rather than a production agent platform. Neither belongs in the lean v1 runtime. Archive or remove them unless an approved near-term experiment names their owner, metric, and expiry.

## 8. Database and deployment truth are fractured

The Compose initializer mounts migrations only through `0021`. CI applies through `0027`. There is no migration runner for upgrades, and Postgres init scripts never rerun on an existing volume.

That means:

- a fresh standard Compose database is behind CI;
- an existing volume is behind unless someone manually applied migrations;
- current API behavior depends on columns and constraints the default deploy may not have;
- the repo has no single, repeatable schema state transition.

One migration runner must be used by local bootstrap, CI, staging, production deploy, and restore. This is more important than rearranging folders.

The release checker also reports a rollback artifact as present because some images are built. Those images are the old Rust/React topology; there is no Node API image to roll back to. The cutover condition must be candidate-specific and service-specific.

## 9. The core Quran-learning loop is still nonfunctional

The architecture duplication is not the deepest product problem. The real audio-to-reviewed-feedback chain currently breaks in two independent places.

### Real finalization persists zero usable alignments

`ml-inference#predictAlignment` returns `wordId`, text, status, and confidence, but no `startMs` or `endMs`. Rust `finalize_session` passes absent spans through as null. `persist_alignments_in_tx` deliberately rejects any span that does not satisfy `0 <= startMs < endMs`.

That safety rule is correct: a word without a usable time span cannot anchor a Tajweed finding to evidence in the recording. The integration result, however, is that the real finalization path persists zero alignment rows. Rust integration tests use an ML mock that supplies timestamps, so the tested chain is stronger than the deployed ML response.

Without stored alignments, predicted Tajweed findings cannot attach to evidence, enter a meaningful teacher-audio review, or become durable learner feedback.

### Rule-based Tajweed can never clear the learner gate

The active Tajweed engine analyzes canonical written text, not the learner's acoustic performance. `NO_MEASURED_CONFIDENCE` is deliberately `0`, and every real rule finding carries that value. Teacher acceptance changes the review status, but the learner gate also requires confidence of at least `0.82` and a source.

Therefore teacher acceptance alone still cannot show these findings to a learner. This is safe behavior, but it means the shipped “Tajweed coach” has no functional learner-facing result. The system detects rules present in the verse, not mistakes made by the learner.

### Model and evaluation claims are not release proof

- Standard Compose pins generic Whisper `base`; the Quran-tuned checkpoint named in code is not installed in that image.
- Full-session ASR is capped at 120 seconds, creating a hard failure for longer recitations.
- Alignment responses label `ml-aligner-v0.2`, persistence defaults to `model-v0.3`, and Tajweed selects a database row by kind; provenance does not reliably name the producing implementation.
- `golden-evals.json` and the original internal SQL seed contain fixed threshold-passing metrics. The runtime `createEvalRun` copies fixtures rather than recomputing model performance.
- `golden-regression.test.mjs` validates deterministic fixture/canonical behavior, not learner audio accuracy, and the canonical `verify.sh` does not run it.
- Migration `0027` correctly removes one unevidenced database claim, but the platform still lacks a candidate-bound Kurdish/Quran recitation evaluation.

### Canonical provenance still needs repair

The full-Quran files and manifest say `alquran.cloud`, but the SQL seed generator builds import bundles with source id `tanzil`. Database provenance can therefore disagree with the bytes' documented source.

The global full-Quran hash covers ayah text, not the parallel `words` arrays used by alignment. Import-bundle checksums exercise generated word records, but there is no independently pinned full-corpus word-token hash in the manifest. A same-count token drift can evade the global content hash.

These are release blockers regardless of whether the backend language is Rust or Node.

## 10. Repository clutter versus real complexity

The tracked repository contains 69 spec directories and 263 spec files. The current-state docs still describe React/Rust as the implemented architecture, while migration specs describe Flutter/Node. Root commands, Compose, runbooks, and architecture documentation disagree.

Some large disk usage is ignored build/cache output—Rust `target`, Flutter build/tool state, Python virtual environments—not source architecture. Cleaning disk caches may improve developer ergonomics but will not produce a coherent product.

After cutover, retain only:

- one current architecture document;
- decisions that still constrain behavior;
- testing and operations runbooks;
- one active spec per active feature;
- generated release evidence outside the source tree.

Completed specs can be removed from the active branch after a migration summary points to their commits. Git history is the archive; adding another giant `legacy/` tree would preserve the clutter under a new name.

## 11. Recommended target architecture

```text
apps/
  flutter/                 one learner/teacher/scholar client
server/
  package.json             one Node package and dependency boundary
  src/
    api/                   Fastify REST, auth, RLS-scoped domain handlers
    realtime/              WebSocket tickets, replay, backpressure, audio ingress
    domain/                recitation, progress, review, privacy, approvals
    inference/             alignment/Tajweed orchestration
    workers/               CPU work and background jobs; not on the API event loop
packages/
  quran-data/              immutable canonical and reviewed translation bundles
  contracts/               OpenAPI, generated clients, shared fixtures and gates
infra/
  migrations/              one ordered runner used everywhere
tests/                     contract, integration, device, security, reliability
```

Production dependencies remain explicit: Postgres, private object storage, and temporarily the private ASR worker. A small number of deployable process roles from one Node package is still one backend. Forcing WebSocket, API, and CPU inference onto one event loop just to claim “one process” would be cosmetic simplification.

### Single sources of truth

- One declarative route inventory generates the Fastify registration and OpenAPI contract.
- OpenAPI generates the Dart client/models; do not hand-maintain three client API layers.
- Server-issued session metadata owns model and dataset identity; clients do not invent checksums.
- Postgres owns durable ticket consumption, audio indexes, outbox/jobs, and tenant isolation where practical, avoiding Redis/NATS for a small deployment.
- Cross-runtime fixtures continue to pin Quran bytes, enums, consent, feedback visibility, tickets, and privacy behavior.

## 13. Non-negotiable cutover gates

Rust/React deletion is allowed only when all of these are true:

1. The route inventory recognizes all 42 current operations, or an approved smaller target contract explicitly removes some.
2. Flutter's required operations are implemented by Node with no Rust upstream.
3. Node has rate limiting, maintenance mode, RLS-role boot refusal, timeouts, cancellation, graceful shutdown, and deep readiness.
4. Node realtime passes ticket, replay, origin, hostile frame, backpressure, reconnect, lost-chunk, retention, and audio-index tests.
5. One migration runner takes an empty database and the previous production schema to the same checksum.
6. Real audio produces usable word spans, durable findings, and calibrated learner-safe feedback; mocks cannot be the only passing chain.
7. Flutter passes Kurdish/Arabic review, main learner/teacher journeys, accessibility, physical Android/iOS tests, and signed release builds.
8. The real deploy graph uses Flutter/Node and has candidate-bound images/artifacts, monitoring, rollback, and restore evidence.
9. Rust/React receive no traffic for a bounded observation window and rollback is rehearsed.
10. Security, privacy, scholar, accessibility, and operations owners sign the exact candidate.

## Final answer

Clean this repository. Do not start over. But do not confuse deleting folders with completing the migration.

The next correct phase is a consolidation plan that first repairs the false-green inventory and deployment schema, then finishes Node as a standalone backend, then closes the minimum Flutter product gaps, and only then deletes Expo, React, and Rust in that order of proven replaceability.
