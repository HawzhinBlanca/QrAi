## What this changes

`FL9` was recorded as *"needs Xcode + hardware this machine does not have."* Half of that is now
wrong, and the wrong half is the actionable one.

| | then | now |
|---|---|---|
| Xcode | absent | **`/Applications/Xcode-beta.app` is installed** |
| `xcode-select` | — | still points at `/Library/Developer/CommandLineTools` |
| `xcodebuild`, `simctl` | absent | still absent, *because of the line above* |
| Android cmdline-tools | missing | still missing, licences unaccepted |

So iOS/macOS is blocked by **one line**, not by a missing multi-gigabyte install:

```
sudo xcode-select -s /Applications/Xcode-beta.app/Contents/Developer
sudo xcodebuild -runFirstLaunch
```

Note the path: `flutter doctor` prints `/Applications/Xcode.app`, which does **not** exist here. The
install is the beta. Following the tool's own message verbatim would fail.

Both commands need a password, so they are the owner's to run. Android needs a second, separate
thing — `cmdline-tools` plus `flutter doctor --android-licenses`.

## What is still true

`FL9` stays OPEN. Selecting Xcode makes an iOS **simulator** reachable; it does not produce a
physical device, and it does not execute the recorder's hardware path — AUD1 already recorded that
"every test injects the PCM stream, so what is asserted is ordering and routing, not that a
microphone opens." A simulator's microphone is the host's, which is closer to proof than a widget
test and still not a phone.

Nothing in this file is a claim that the app runs on a device. It is a record of why nobody can say
either way from this machine, and of the exact commands that would change that.
